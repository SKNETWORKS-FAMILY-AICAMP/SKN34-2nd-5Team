# 관리자 화면 QA 계획

작성 기준: 2026-08-04  
최종 수정: 2026-08-05  
대상: React `app/` + FastAPI `api/` + 인증 서비스 `auth_service/` + MySQL `yelp_data`

## 1. 목적

관리자(`ADMIN`)가 로그인한 뒤 리뷰 공급 위험을 확인하고, 리뷰어를 검토하고,
관리자 판단과 접촉 이력을 남기고, 개인·권역 운영안을 저장하고, 운영 결과와 계정을
관리하는 전체 흐름이 화면과 서버에서 일관되게 작동하는지 확인한다.

이 문서는 다음 문서와 함께 사용한다.

- [관리자 UI QA 테스트 케이스](ADMIN_UI_QA_CASES.md)
- [관리자 UI QA 흐름도](ADMIN_UI_QA_FLOWS.md)
- [최신 QA 실행 결과](ADMIN_UI_QA_EXECUTION_2026-08-05.md)

## 2. 테스트 기준

### 2.1 현재 구현 기준 경로

| 기능 | 현재 경로 | 비고 |
|---|---|---|
| 콘텐츠 공급 위험 | `/` | 도시·권역, 공급·핵심 리뷰어·신규 유입 관점 전환 |
| 핵심 리뷰어 관리 | `/reviewers` | URL 필터, 10행 페이지네이션, Reviewer 360 진입 |
| Reviewer 360 | `/reviewers/:reviewerId` | 판단·메모·스누즈·접촉 이력 서버 저장 |
| 운영안 설계 | `/playbook` | 개인·권역 대상 명단 및 운영안 서버 저장 |
| 콘텐츠 네트워크 | `/content-network` | 메뉴와 Command Palette에는 없고 직접 경로로만 접근 가능 |
| 운영 결과·알림 | `/operations-history` | 알림, 운영안, 대상 명단, 판단, 접촉 이력 |
| 운영 신뢰 | `/trust` | 모델·데이터·한계·시뮬레이션 |
| 설정 | `/settings` | `ADMIN`만 사용자·권한 관리 가능 |

`/regional`, `/regional/home`은 현재 `/`로 이동한다. `/individual/home`은 핵심
리뷰어 미검토·우선순위 큐로 이동한다. 이전 UI 문서의 독립 `/regional` 화면을
기대 결과로 두지 않는다.

### 2.2 표현·데이터 판정 기준

- `risk_score`와 클래스 점수는 확률이 아니라 운영 우선순위용 모델 점수다.
- `이탈 가능성 n%`처럼 확률로 단정하는 문구가 없어야 한다.
- 지리 정보는 `리뷰 활동 반경`, `맛집 탐방 반경`, `주 활동 권역`으로 표현한다.
- 거주지·직장·실제 이동 경로를 추론하는 문구가 없어야 한다.
- 2019년 사후 검증 데이터는 기본 숨김이며 운영 당시 정보와 분리한다.
- 개인·권역 운영안 저장은 실제 메시지 발송이 아니다.
- 데모·합성 데이터가 사용되면 화면에 명확히 표시되어야 한다.

## 4. 시작 조건

- 테스트 시작 전에 배포 환경, 배포 완료 시각, 커밋 또는 빌드 식별자를 실행 보고서에 기록한다.
- 식별자를 제공받지 못한 경우 `확인되지 않음`으로 기록하고 최종 배포 승인 근거로 사용하지 않는다.
- 실행 도중 배포가 변경되면 변경 시각을 기준으로 결과를 분리하며, 영향받은 케이스는 새 배포에서 다시 실행한다.
- MySQL `yelp_data`와 필요한 v05 운영 테이블이 준비되어 있다.
- 인증 서비스가 `8100`, 분석 API가 `8000`, React가 `5173`에서 실행된다.
- `/health`, `/auth/api/me`, `/api/operations`, `/api/reviewers`가 정상 응답한다.
- 관리자 테스트 계정과 별도의 운영자·조회 전용·승인 대기 계정이 있다.
- 화면에 표시되는 실제 리뷰어 중 아래 조건의 ID를 실행 직전에 기록한다.
  - 관리자 판단이 없는 CRM 대상 1명
  - 관리자 판단이 있는 대상 1명
  - 음식점 추천이 1곳 이상 있는 대상 1명
  - 가능하면 스누즈를 오늘/과거로 만들 수 있는 대상 1명
- 브라우저는 관리자용과 권한 비교용 프로필을 분리한다.

## 5. 테스트 데이터와 정리 규칙

| 데이터 | 규칙 |
|---|---|
| 테스트 계정 | `qa_YYYYMMDD_용도` 형식 사용 |
| 대상 명단 | `QA-YYYYMMDD-시나리오` 형식 사용 |
| 판단 메모 | `[QA YYYY-MM-DD]` 접두어 사용 |
| 접촉 메모 | `[QA] 채널 동작 확인`처럼 식별 가능하게 작성 |
| 운영안 제목 | `QA-YYYYMMDD-개인` 또는 `QA-YYYYMMDD-권역` |
| 스누즈 | QA 종료 후 판단 취소 또는 정상 날짜로 복구 |

관리자 판단 취소는 감사 이력을 남기므로 완전 삭제가 아니다. 테스트 시작 전에 선택한
리뷰어와 원래 판단·메모·스누즈를 기록하고, 종료 후 원래 상태로 복구한다. 생성 계정은
UI에 삭제 기능이 없으므로 전용 QA DB를 우선 사용하고, 남겨야 하면 비활성화한다.

## 6. 우선순위와 결함 등급

| 구분 | 의미 | 예시 |
|---|---|---|
| P0 | 배포/발표 차단, 반드시 매 실행 | 로그인 불가, 전체 빈 화면, 판단/운영안 저장 실패 |
| P1 | 핵심 업무 훼손 | 필터 오류, 잘못된 리뷰어 저장, 권한 우회, 영속성 실패 |
| P2 | 보조 기능·표현·접근성 | 키보드 이동, 작은 화면 배치, 보조 문구 |

| 심각도 | 판정 |
|---|---|
| S1 Blocker | 서비스 진입 불가, 데이터 손상, 다른 대상에 쓰기, 관리자 권한 상실 |
| S2 Critical | 핵심 저장/조회/권한 통제가 실패하거나 결과가 사실과 다름 |
| S3 Major | 우회 가능한 기능 오류, URL 복원·필터·지도 동기화 실패 |
| S4 Minor | 오탈자, 간격, 비핵심 접근성·표현 문제 |

## 9. 증적 기록

각 테스트 실행 시 다음을 남긴다.

- 실행자, 실행 일시, 브라우저/해상도, 빌드 또는 커밋 해시
- 배포 환경·배포 완료 시각과 QA 시작·종료 시각, 실행 중 추가 배포 여부
- 테스트 ID, `PASS`/`FAIL`/`PARTIAL`/`NOT RUN`, 실제 결과
- 실패 화면 캡처와 Console 오류
- Network 요청의 메서드·경로·상태 코드(쿠키·비밀번호·CSRF 값은 마스킹)
- 저장 케이스는 새로고침 후 화면 증적 또는 API/DB 확인 결과
- 결함 ID와 재현율

## 10. 종료 조건

- P0 100% 통과
- P1 100% 실행, 미해결 S1/S2 없음
- 저장·수정·취소·이력·권한·세션 케이스가 새로고침 후에도 일치
- 1440×900에서 핵심 상태와 Primary CTA가 잘리지 않음
- 작은 화면에서 기능이 숨겨지지 않고 필요한 표에만 내부 가로 스크롤이 존재
- `npm run lint`, `npm run build`, 인증 서비스 테스트 및 관련 API 테스트 통과
- 테스트 데이터 복구/비활성화 완료
- 최종 배포 변경 회귀 `UPD-01~07`이 모두 실행되고 미해결 P1 실패가 없음

## 11. 구현상 집중 확인 지점

- React의 역할 제어는 UX 처리이고 최종 보안 경계는 서버다. 버튼 상태뿐 아니라 직접
  API 요청의 401/403도 확인한다.
- 판단과 접촉 이력은 Reviewer 360에서 역할에 따라 비활성화되지만, 운영안 저장 화면도
  서버가 `VIEWER` 쓰기를 거부하는지 별도로 확인한다.
- 임시 비밀번호는 계정 생성 직후 한 번만 표시된다. 화면 재진입 후 다시 노출되면 안 된다.
- 권역 캠페인 저장은 대상 명단과 운영안을 연속 생성한다. 두 번째 단계 실패 시 고아 명단
  발생 여부를 결함으로 기록한다.
- URL 파라미터는 화면 상태의 일부다. 새로고침·뒤로가기·잘못된 값 입력을 반드시 확인한다.

## 12. 정적 점검에서 확인된 선행 리스크

아래는 테스트 실행 결과가 아니라 2026-08-04 소스 기준으로 우선 재현할 항목이다.

- 인증 DB에는 `must_change_password`가 저장되지만 로그인 처리에서 비밀번호 변경
  화면으로 강제 이동하는 흐름은 확인되지 않았다. `SET-20`이 실패할 가능성이 높다.
- Reviewer 360과 운영 알림에는 읽기 전용 제어가 있으나 운영안 설계 화면의 쓰기 버튼은
  역할별 비활성 처리가 일관되게 연결되어 있지 않다. 서버 403과 함께 `REL-06`에서 UI
  피드백도 확인한다.
- 일부 분석 조회 API는 라우터 자체에서 인증 의존성이 보이지 않는다. 배포 환경의 Nginx
  보호를 포함해 비로그인 직접 API 접근 범위를 별도 확인해야 한다.
- 권역 캠페인은 대상 명단 생성 뒤 운영안을 생성하는 두 요청이다. 운영안 생성만 실패하면
  대상 명단이 남을 수 있으므로 `REL-04`에서 부분 저장 여부를 확인한다.
- 콘텐츠 네트워크는 구현 경로가 있지만 현재 전역 메뉴와 Command Palette에서 발견할 수
  없다. 의도된 숨김인지 누락인지 제품 결정이 필요하다.
