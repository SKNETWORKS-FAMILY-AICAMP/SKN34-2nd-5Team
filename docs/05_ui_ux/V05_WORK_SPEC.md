### 2.7 반경 가설의 검증 결과 (중요)

[feature_validation_report.md](../03_data_and_models/feature_validation_report.md) §7:

- 유지 P90 반경 중앙값 14.29km / 이탈 10.31km
- 반경 축소 중앙값 유지 0.63km / 이탈 2.95km
- **음식점 수를 통제하면 일관된 차이가 사라진다** (원인: 여행 리뷰와 활동 음식점 수)
- 활동 중심 100km 이상 이동: 유지 3.06% / 이탈 6.60%
- 판정: **탐방 반경 축소는 핵심 가설로 기각**. `log_p90_radius_decline` 실험용,
  `log_center_shift` 보조 후보, 실제 생활권 이동은 판단 불가. **모델 43개 피처에 미포함.**

→ 반경은 **위험 지표로 쓰지 않는다.** 오탐 판별(여행 vs 실제 축소), 근거 확인,
추천 범위 산정에만 쓴다.

### 2.8 위험 유형과 판단 선택지

`classify_risk_type()`([insights.py:147](../../shared/retention/insights.py))이 만드는 5개:
`복합 위험형` · `활동량 붕괴형` · `작성 주기 이완형` · `탐색 활동 축소형` ·
`일반 모니터링형`. 전부 관찰 언어이며 **"미식 번아웃"은 코드 어디에도 없다**(기획
문서와 노트북에만 존재).

관리자 판단 4개: `리뷰 다시 시작 유도` · `리뷰 활동 늘리기` · `변화 지켜보기` ·
`이번엔 제외`.

**`탐색 활동 축소형`은 지리적 반경이 아니라 `unique_business_decline_rate`(음식점
개수) 기준이다.** 반경 시각화를 이 유형 옆에 놓을 때 라벨을 구분해야 한다.

## 3. 철회한 이전 판단

| 철회 대상 | 사유 |
|---|---|
| **Retention Pulse** (priorityRank 순 100명 단위 타일) | 정렬 결과의 앞부분을 색칠하는 동어반복. 상위 20%가 첫 줄에 오는 건 정의상 당연하다. → **Signal Atlas**로 대체 |
| **다음 리뷰어 프리페치** | `detailPromise`가 이미 전체를 캐시한다. 네트워크 재호출이 없어 무의미. 깜빡임의 원인은 remount 시 state 초기화 |
| **0.6초 자동 다음 이동** | 저장 결과 확인·수정·플레이북 확인 기회를 뺏는다. → 명시적 결합 액션 + 확인 바 |
| **"데이터가 없으니 기능을 뺀다"** | 운영 데이터(우리가 만드는 것)와 관찰 데이터(Yelp에서 와야 하는 것)를 혼동했다. 운영 데이터는 전부 구현 가능 |
| **13MB 정적 JSON 우려** | API 전환이 이미 끝났다. 단 `/api/reviewer-details`가 전체를 한 응답으로 반환하는 문제는 별도로 존재 |
| **"리뷰 공급 변화" 지표 삭제** | 아티팩트 원인이 코호트 선정 편향이므로 **재설계로 고칠 수 있다** (3.1 참조) |
| **Intervention Path** (얇은 5단계 스트립) | 설명 장치일 뿐 역할 차이가 안 보인다. → **Decision Rail**로 강화 |
| **Trust Center의 v02/v03 비교 노출** | 발표의 핵심 질문("왜 상위 20%인가")과 거리가 있다. → **Review Capacity Dial** 우선 |
| **지도 커버리지 배너** | 묻지 않은 것을 먼저 해명하면 미완성으로 읽힌다. Trust Center 적용 범위로 이동 |

### 3.1 "리뷰 공급 변화"가 고쳐지는 이유

모든 권역에서 +50~145% 증가로 나오는 원인은 **코호트 선정 편향**이다. 2018년에
선정된 리뷰어만 세니 2018년이 당연히 높다. 코호트가 아니라 **전체 리뷰**로 권역별
연도 리뷰 수를 세면 편향이 사라진다(`restaurant_reviews.parquet` ↔
`restaurant_businesses.parquet`). 그러면 "이 권역의 콘텐츠 공급이 실제로 늘고 있나
줄고 있나"라는 유효한 지표가 된다.

## 4. 작업 목록

### A. 프런트 — 시각

#### A-1. Signal Atlas (운영 홈 대표 장면)

- **목적**: 6,533명의 활동 신호 공간에서 검토 대상이 어디에 몰려 있는지 발견한다.
- **축**: X = 마지막 리뷰 후 경과일(구간), Y = 최근 활동 월(3~12)
- **인코딩**: 셀 밀도 = 인원, **색 = 검토 대상 비율(확정)**, 테두리 = 상위 20% 강조
- **렌더 방식**: **개별 산점도 금지.** Y가 10개 이산값이라 6,533점이 10개 줄무늬로
  뭉개진다. **밀도 격자**(2.3의 표가 그대로 화면)로 만든다. 순수 CSS grid 또는 SVG,
  신규 라이브러리 불필요.
- **데이터**: `recentRecencyDays`, `recentActiveMonths`, `crmTarget`, `modelJudgment`,
  `riskType` — 전부 기존 필드. 신규 데이터 0.
- **상호작용**: 셀 클릭 → 해당 조건이 필터로 걸린 `/reviewers`로 이동(B-6 필요).
- **구간 경계값(확정)**: 경과일 0/15/45/90/180일. 인원 분포 31.6% / 29.7% / 19.8% /
  14.3% / 4.5%로 뒤로 갈수록 줄지만 극단적 쏠림은 아니라 재조정 없이 확정.
- **주의**: 경계 지대(42%, 73%)를 시각적으로 드러낼 것. 이 부드러운 전이가 Atlas가
  동어반복이 아님을 보여주는 지점이다.

#### A-2. Decision Rail (Reviewer 360)

- **목적**: "모델은 참고, 결정은 사람"을 한 장면으로 전달한다.
- **구조**: 3개 영역 — `관찰된 활동 변화` / `모델 판단(참고)` / `관리자 판단(결정)`,
  그 뒤에 `플레이북`이 관리자 판단 이후 활성화
- **시각 위계**: 관찰 = 중립색 / 모델 = 아웃라인 / 관리자 = 채운 강조색 /
  플레이북 = 판단 전 비활성
- **데이터**: `coreChange`, `riskType`, `modelJudgment`, 저장된 판단,
  `strategyFor()` — 전부 기존. 신규 계산 0.
- **주의**: 화살표가 인과로 읽히지 않게 "확인 순서" 캡션 필요.

#### A-3. Activity Story Stage (Reviewer 360)

- **목적**: 2017 비교 기간과 2018 최근 기간의 차이를 하나의 무대로 보여준다.
- **구조**: 지표 4행(리뷰 수 / 활동 월 / 작성 간격 / 탐색 음식점)을 좌우 대비로,
  각 행마다 다른 시각 인코딩(막대 / 점 / 간격 눈금 / 마름모)
- **상호작용**: `EvidenceList` 항목 선택 시 대응 행 강조(B-5와 연결)
- **데이터**: `changes`, `activitySummary`, `intervalComparison` — 기존.
- **주의**: **직전 활동 없는 1,692명은 2017 쪽이 없다.** 억지 변화율 대신 별도
  상태("직전 연도 활동 없음")로 표시.

#### A-4. Review Capacity Dial (Trust Center 대표 장면)

- **목적**: "왜 하필 상위 20%를 검토하는가"에 답한다.
- **구조**: Top-K 임계값 슬라이더(`/api/trust`의 topK 배열 실제 8개 지점 —
  5/10/15/20/25/30/35/40%. 초기 초안은 4개 지점만 예시로 들었으나 실제 데이터가
  8개 전부 있어 전체를 사용), 현재 정책 표시,
  선택 지점의 검토 대상 · 포착 인원 · 정밀도 · 재현율 · Lift
- **데이터**: `/api/trust`의 `topK` 배열 — **이미 존재한다. 신규 계산 0.**
- **주의**: 슬라이더가 실제로 정책을 바꾸는 것으로 오해되지 않게 "시뮬레이션" 명시.
  저장된 평가 지점만 쓰고 새로 계산하지 않는다.

#### A-5. 콘텐츠 위험 — 도시 버블 맵

- **목적**: 권역 규모·위험을 위치와 함께 보여주고, 광역 분리 문제를 드러낸다.
- **구조**: 14개 대표 도시를 좌표에 버블로. 크기 = 리뷰어 수, 색 = 고위험 비율
  3구간. 필라델피아 광역·세인트루이스 광역은 점선 묶음 + 합계 라벨.
- **투영**: 14개 고정 좌표 하드코딩. **지도 라이브러리·타일 서버 불필요.**
  `albersUsa`는 AB(캐나다)를 버리므로 쓰지 않는다.
- **배경**: 실제 해안선을 그리지 않고 위경도 격자 + 49°N 선만. "위치 모식도" 명시.
- **데이터**: `/api/regional` — **이미 존재한다. 신규 데이터 0.**
- **상호작용**: 버블 ↔ 하단 표 행 상호 하이라이트, 클릭 → 리뷰어 관리로.

#### A-6. 콘텐츠 위험 — 권역 표

- 14행, 정렬 가능(고위험 비율 / 리뷰어 수 / 검토 대상), 유지·약화·중단 구성 막대
- 지도와 같은 화면. 표는 시각화와 경쟁하지 않으므로 "차트 나열" 문제가 없다.

#### A-7. 콘텐츠 위험 — 탐방 범위 뷰 (토글)

- 권역별 P90 반경의 사분위 분포 띠 + 코호트 기준선(유지 14.29 / 상실 10.31)
- **G-3 집계가 선행되어야 한다.**
- 표본이 작은 권역(DE 49 / IL 56)은 띠가 넓어져 불확실성이 자동으로 드러난다.
- 반경을 **위험이 아니라 캠페인 범위 근거**로 표현한다.

#### A-8. Reviewer 360 — 리뷰 활동 반경

- **목적**: 활동 음식점 감소가 여행 리뷰 때문인지 일상 탐방 축소인지 운영자가 판별한다.
- **구조**: 2017·2018 P90 반경 이중 원 + 방문 음식점 산점, 축척 밖 원거리 활동은
  별도 인셋. 중심점은 **점으로 찍지 않고** 기준 십자선만. 절대 좌표 눈금 없음.
- **데이터**: G-5 필요.
- **주의**: 이 프로젝트에서 도메인 위험이 가장 높은 화면. 7절 문구 규칙 필수 적용.

0.75~0.8배로 왜곡되어 "P90 원 안인데 밖에 그려진 점"이 생긴다. 중심 위도 기준 코사인
보정 또는 haversine 거리+방위각 극좌표 배치 중 선택 필요.

### H. API

- **H-1. `/api/reviewer-details` 분할**: 현재 전 리뷰어 상세를 한 응답으로 반환한다.
  리뷰어 단건 엔드포인트로 바꾸고 프런트는 필요한 리뷰어만 요청한다. (B-11과 함께
  설계할 것 — 캐시 전략이 바뀐다.)
- **H-2. 판단 CRUD**: F절 테이블용 엔드포인트.
- **H-3. 반경 단건 조회**: G-5용.
- **H-4. 추천 음식점 조회**: G-1용.

```
decisions
  id                PK

  sample_id

  note              TEXT NULL

  model_version     VARCHAR      -- 참조용. 키가 아니다
  created_at / updated_at

  id / decision_id / reviewer_user_id
  from_decision / to_decision / actor_id / changed_at

  id / name / role / active

interactions

campaigns
```

**판단 키 설계 주의.** 현재 localStorage 키는 `` `${modelVersion}::${sampleId}` ``다.
모델이 v05로 바뀌면 기존 판단이 전부 미검토로 리셋된 것처럼 보인다. 서버에서는
**판단을 리뷰어에 귀속시키고 `model_version`은 참조 컬럼으로만** 둔다.

마이그레이션은 하지 않는다(9.1 확정). 기존 localStorage 판단은 폐기되고 F-1 배포
시점부터 서버에 새로 쌓인다.

## 6. 모델 버전 독립 계약

모델(ML·DL)이 확정된 뒤 병합한다. 그때 프런트를 다시 손대지 않으려면 **필드명이
모델과 무관하게 고정**되어야 한다. ML·DL 파트와 합의할 항목:

| 필드 | 의미 | 비고 |
|---|---|---|
| `modelVersion` | 모델 식별자 | 화면에 표시 |
| `modelJudgment` | 유지 우세 / 약화 우세 / 중단 우세 | 문자열 3종 고정 |
| `scores` | 클래스별 점수 | **보정 확률이 아님** |
| `priorityScore` / `priorityRank` / `priorityTopPercent` | 통합 우선순위 | |
| `crmTarget` | 상위 20% 여부 | 임계값이 바뀌면 명시 |
| `riskType` | 5개 유형 | 규칙 기반, 모델 무관 |
| Top-K 배열 | `targetRate` / `targetUsers` / `captured` / `precision` / `recall` / `lift` | A-4가 그대로 사용 |
| 성능 지표 | macroF1 / macroPrAuc / macroRocAuc / balancedAccuracy | |

**프런트는 v04 수치를 하드코딩하지 않는다.** 현재 값(0.552 / 0.579 / 0.756 / 0.565,
정밀도 87.4% / 재현율 28.9% / Lift 1.45)은 전부 API에서 온다.

## 7. 화면 문구 규칙

**남길 것** — 오독하면 운영 판단이 틀리는 것

- 점수가 실제로 보이는 곳에 한 번: *클래스 점수는 보정 확률이 아니며 통합 점수는
  운영 우선순위에 사용합니다.* (여섯 화면 푸터 반복은 제거)
- 지도·반경 화면에만: *리뷰 활동 지역이며 거주지·직장·생활권을 나타내지 않습니다.*
- 반경 화면에만: *반경 축소는 v04 검증에서 위험 예측 피처로 채택되지 않았습니다.*
- Decision Rail: *확인 순서이며 인과관계를 의미하지 않습니다.*
- 사후 정답(`actual.*`)은 `validationMode` 밖에서 노출하지 않는다 (현행 유지)

**쓰지 않을 것**

- "미식 번아웃" — UI 라벨로 쓰지 않는다. 코드의 5개 유형명이 이미 관찰 언어이므로
  *의학적 상태를 의미하지 않습니다* 푸터도 불필요해진다
- "이탈 가능성 84%" 형태의 확률 표현
- 개입의 예상 효과·성과 추정
- 데이터셋 커버리지 해명 (→ Trust Center 적용 범위)
- 미구현 기능 목록·상태 배지

## 9. 결정 사항

### 9.1 확정 (2026-07-31)

1. **Signal Atlas 구간 경계값** — 0/15/45/90/180일로 확정(4.1 참조). 재조정 없음.
2. **Atlas 색 인코딩** — **검토 대상 비율**로 확정. 화면 목적("어디를 먼저 볼까")에
   직접 답한다는 이유로 모델 판단 우세 대신 선택. 다만 이 인코딩은 정의상 우세/열세
   경계를 다시 그리는 것이라 예측처럼 보일 위험이 있다 — Atlas 근처에 "관찰된 활동
   신호의 밀집도이며 개별 확률이 아닙니다" 문구를 붙인다.
3. **권역 정의** — **주(state) 단위 유지**. metro 재계산 안 함. 지도(A-5)에서 광역
   분리(필라델피아·세인트루이스)를 시각적으로만 드러낸다. 파이프라인·`DEC-` 문서 불변.
4. **localStorage 판단 마이그레이션** — **하지 않음**. 기존 브라우저 판단은 테스트
   데이터로 폐기하고, F-1 배포 시점부터 서버에 새로 적재한다. 마이그레이션 스크립트
   불필요 — 5절 스펙에서 관련 언급 없음.

### 9.2 남은 기술 판단 (구현 시 내가 정함, 결과만 공유)

5. **`/api/reviewer-details` 분할 시 캐시 전략** — 단건 요청으로 바꾸며
   `detailPromise` 단일 캐시를 리뷰어별 캐시 맵으로 전환.
6. **G-5 좌표 투영 방식** — haversine 거리+방위각 극좌표 배치. 코사인 근사보다
   계산이 한 단계 더 들지만, 반경 판별 도구(A-8)에서 "P90 원 안인데 밖에 그려진 점"이
   생기면 도구 자체의 신뢰가 깨지므로 정확한 방식을 우선한다.
7. **탐방 범위 뷰(A-7)** — 포함 확정("모두 진행" 전제). G-3(권역별 반경 집계) 선행 필요.
