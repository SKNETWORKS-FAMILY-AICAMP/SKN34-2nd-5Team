# v05 고도화 방향 탐색 (설계 검토 단계 — 코드 변경 없음)

> 이 문서는 조사·아이디어 발굴 결과물이다. 파일 수정은 없었고, 여기 나온 어떤 아이디어도
> 구현 승인을 받은 것이 아니다. 구현으로 넘어가려면 대상 화면·변경 파일·이유·기존 기능
> 영향도를 먼저 설명하고 별도 승인을 받는다.

## 1. 현재 서비스의 핵심 문제 진단

코드 확인 범위: [`app/src/pages/OperationsPage.jsx`](../../app/src/pages/OperationsPage.jsx),
[`ReviewerListPage.jsx`](../../app/src/pages/ReviewerListPage.jsx),
[`ReviewerDetailPage.jsx`](../../app/src/pages/ReviewerDetailPage.jsx),
[`PlaybookPage.jsx`](../../app/src/pages/PlaybookPage.jsx),
[`RegionalRiskPage.jsx`](../../app/src/pages/RegionalRiskPage.jsx),
[`TrustCenterPage.jsx`](../../app/src/pages/TrustCenterPage.jsx),
[`decisionStorage.js`](../../app/src/services/decisionStorage.js),
[`DecisionPanel.jsx`](../../app/src/components/reviewer-detail/DecisionPanel.jsx),
[`PriorityQueue.jsx`](../../app/src/components/operations/PriorityQueue.jsx).

**a. 여섯 화면 모두 같은 골격을 쓴다.** `상단 라벨 → h1 → 설명 → SummaryCard/MetricCard 그리드
(rounded-xl border bg-white) → 필터 pill → 표 또는 리스트`. 색상 팔레트(`#137A5A` 그린,
`#DDE4DF` 보더)까지 동일해서, 화면을 바꿔도 "같은 대시보드를 계속 보는" 인상을 준다.

**b. 카드 밀도가 높다.** `rounded-xl border bg-white p-5/p-6` 패턴이 6개 화면에 약 30곳
반복된다. 정보량 대비 여백·구분선 활용이 적어 화면이 다 비슷한 무게로 보인다.

**c. "판단이 끝나면 다음이 명확하다"는 원칙이 절반만 구현돼 있다.** `DecisionPanel.jsx`를
보면 이미 이전/다음 리뷰어 링크가 판단 저장 버튼 바로 아래 있다 — 좋은 구조다. 하지만
저장 후 자동으로 다음 미검토 대상으로 넘어가지 않고, 사용자가 직접 "다음 리뷰어"를 눌러야
한다. 즉 뼈대는 있는데 마지막 한 걸음이 비어 있다.

**d. 근거→모델 판단→관리자 판단→플레이북의 연결이 화면 간에 흩어져 있다.**
`ReviewerDetailPage.jsx`는 `EvidenceList` → `strategyFor()` 추천 → `DecisionPanel`을
세로로 쌓아 보여주지만, 이 넷이 "하나의 판단 경로"라는 시각적 신호(연결선, 단계 표시)는
없다. 플레이북 화면(`PlaybookPage.jsx`)은 `?reviewer=` 쿼리로 딥링크되지만 도착 후에는
다시 별도 리스트 화면일 뿐이다.

**e. 대표 장면이 없다.** 6,533명 데이터가 있는데 이를 한 화면에서 조망하는 곳이 없다.
운영 홈(`OperationsPage.jsx`)의 진입 장면은 숫자 3개(`SummaryCard`)뿐이라 "정지 화면 한
장"으로 프로젝트 차별성을 설명하기 어렵다.

**f. 트리아지 인프라는 이미 있는데 안 쓰인다.** `PriorityQueue.jsx`는 이미 순위·색상·판단
상태를 압축해서 보여주는 밀도 있는 리스트다 — Linear/Stripe식 큐의 씨앗이 이미 심겨
있다. 다만 5명만 보여주고 키보드 조작이 없다.

**g. Trust Center는 이미 버전 비교를 갖고 있다.** `v03?.available`, `v02?.available`
블록이 `<Expander>`(접힌 `<details>`)로 이미 v02→v03→v04 성능 비교를 제공한다. 문제는
"없어서" 가 아니라 "기본 접힘 상태라 안 보인다"는 것. 지난 대화에서 필자가 제안했던
"버전 히스토리 카드"는 사실 새 기능이 아니라 **이미 있는 것을 펼쳐서 보여주는 문제**다.

## 2. 현재 화면에서 유지해야 할 장점

- **도메인 안전장치가 코드 레벨에 이미 박혀 있다.** `RegionalRiskPage.jsx`는 "거주지가
  아닌 리뷰 활동 지역"이라고 명시하고, `PlaybookPage.jsx` 푸터는 "의학적 상태를 의미하지
  않습니다"라고 쓴다. `ReviewerDetailPage.jsx`의 `validationMode` 체크박스는 사후 정답을
  기본적으로 숨긴다. 이 원칙들은 새로 만들 필요 없이 v05에서도 그대로 지켜야 하는 좋은
  기준선이다.
- **모델 판단과 관리자 판단이 데이터 구조부터 분리돼 있다.** `judgmentToDecision`(모델
  라우팅)과 `decisionStorage`(관리자 실제 판단)는 별개 값이고, `PlaybookPage.jsx`의
  `managerDecisionCounts` vs `pendingModelRouteCounts`도 절대 섞이지 않는다. 이건 "Model
  Decision Lens" 아이디어가 사실 이미 절반 구현돼 있다는 뜻이다.
- **저장 범위 고지가 이미 문장으로 존재한다.** `DecisionPanel.jsx` 하단 안내문("이
  브라우저에만 저장", "담당자·CRM·감사 이력은 아직 연결되지 않았습니다")은 v05에서도
  반드시 유지해야 할 정직성 장치다.
- **리뷰어 상세의 previous/next 네비게이션**과 **키로 스코프된 `decisionStorage`**는
  Triage Focus Mode의 데이터 기반이 이미 갖춰져 있다는 신호다.

## 3. 외부 서비스 벤치마크 표

공식 출처를 직접 확인(WebFetch)한 항목과, 공식 자료에서 UI 세부사항을 찾지 못해
마케팅 설명 수준에 머문 항목을 구분했다.

| 서비스 | 확인 상태 | 핵심 UI 사실 | 프로젝트 적용 아이디어 |
|---|---|---|---|
| **Stripe Radar — Manual Review** | 공식 문서에서 UI 구조 확인됨 | 리스트에 리스크 레벨·고객·결제수단·금액 표시. 선택 시 상세 페이지에 **Risk insights**(위험 근거)와 **Related payments**(연관 근거) 섹션, **이전/다음 버튼**, `J`/`K` 키로 큐 이동, Approve/Refund 등 종료 액션으로 큐 상태 변경 | 이미 있는 이전/다음 리뷰어 네비게이션에 `J`/`K` 단축키 추가 + 저장 시 큐에서 "닫힘" 상태로 표시 |
| **Linear — Triage** | 공식 문서에서 UI 구조 확인됨 | `G T` 단축 이동, 원키 액션(`1` 수락, `2` 중복, `3` 거절, `H` 스누즈), 액션 후 팀 기본 상태로 자동 전이 | 관리자 판단 4개 옵션(변화 지켜보기/리뷰 활동 늘리기/리뷰 다시 시작 유도/이번엔 제외)에 원키 매핑(`1`~`4`), 저장 즉시 다음 미검토 대상 자동 이동 |
| **Salesforce Service Console — Unified Workspace** | 공식 Trailhead에서 UI 구조 확인됨 | 좌측 Split view(케이스 리스트 유지), 중앙 Highlights Panel + Feed(타임라인) + Related Record 사이드바, 하단 Utility Bar | 리뷰어 상세에 "활동 변화 근거 + 판단 히스토리"를 한 화면에서 잃지 않게 배치하는 참고 구조. 단, 별도 사이드 패널/유틸리티 바를 그대로 복제하지는 않음(현재 규모에 과함) |
| **Intercom Inbox — Manager View / Workload Management** | 공식 문서 확인했으나 UI 세부는 제한적 | 확인된 사실: Manager View는 "팀 목표에 맞춘 인박스 뷰", wrap-up 중 "Wrapping up N conversations" 배너 + 카운트다운. 리스트 정렬·카드 디자인은 문서에 없음(마케팅 페이지 수준) | 확인 안 된 부분은 차용하지 않음. "지금 처리 중" 배너 개념만 참고 가치 있음 |

**출처를 확인할 수 없어 사실처럼 쓰지 않은 부분**: Amplitude "triangle chart", Braze
Canvas 노드의 정확한 시각 스타일, Intercom 리스트의 카드 디자인 — 이들은 해석/추정이며
공식 문서 인용이 아니다.

## 5. 외부 서비스에서 발견한 공통 설계 원칙

1. **큐는 "보는 목록"이 아니라 "비워나가는 작업"이다** (Stripe Radar, Linear Triage) —
   액션 하나가 그 항목을 큐에서 제거하고 자동으로 다음으로 넘어간다.
2. **목록에서 상세로 갈 때 문맥을 잃지 않는다** (Salesforce Split View, Stripe Related
   payments) — 리스트가 사라지지 않거나, 상세 화면 자체가 "왜 여기 왔는지"를 계속 보여준다.
3. **근거와 액션이 물리적으로 붙어 있다** (Stripe Risk insights 옆 Approve/Refund
   버튼) — 근거를 스크롤해서 찾고 다른 곳에서 판단하는 구조가 아니다.
4. **원키 단축키는 소수의, 되돌릴 수 있는 액션에만 쓴다** (Linear의 4개 남짓한
   단축키) — 단축키를 늘리는 게 목적이 아니라 반복 작업의 마찰을 줄이는 게 목적.
5. **집계와 개별 탐색은 같은 화면의 다른 층위일 뿐, 다른 도구가 아니다** (Amplitude
   매트릭스 → 셀 클릭 → 사용자 목록).

## 6. 프로젝트에 적용하면 안 되는 패턴

- **Stripe의 Approve/Refund 같은 "즉시 실행되는 종료 액션"** — 이 프로젝트의 관리자
  판단은 CRM 발송이나 계정 조치를 실행하지 않는다. 원키 단축키를 넣더라도 "리뷰어에게
  무언가가 실행됐다"는 인상을 주면 안 되고, 항상 "이 브라우저의 판단 기록"이라는 걸
  명확히 해야 한다.
- **Braze Canvas의 실시간 실행 캔버스** — 조건 분기가 실제로 캠페인을 발송하는 것처럼
  보이면 안 된다. 읽기 전용 "경로도"로만 재해석한다.
- **Salesforce의 Utility Bar/Omni-Channel 전체 프레임워크** — 담당자 배정, 워크로드
  라우팅 같은 기능은 이 프로젝트에 데이터가 없다(`campaignCapabilities`가 이미
  "고도화 예정"으로 명시). 흉내만 내는 비활성 버튼을 새로 추가하지 않는다.
- **Amplitude 코호트 매트릭스를 그대로 이식** — 이 프로젝트는 리뷰어별 월간 시계열은
  있지만(`monthlyActivity`), N일 리텐션 코호트 데이터 구조 자체가 없다. 매트릭스를
  만들려면 새 파생 데이터가 필요하므로 v05 1순위에서 제외.
- **Stripe의 "Risk insights"처럼 확률/스코어를 근거로 직접 제시하는 표현** — 도메인
  원칙상 `risk_score`를 확률처럼 쓰면 안 된다. 대신 관찰된 활동 변화(observable evidence)
  중심으로 표현한다.

## 7. 프로젝트 전용 v05 설계 원칙

1. **전체(6,533명)에서 개인으로 자연스럽게 파고든다** — 집계 화면의 모든 시각 요소는
   클릭하면 워크리스트나 상세로 이어져야 한다. 막다른 장식은 만들지 않는다.
2. **판단이 끝나면 다음 행동이 자동으로 명확해진다** — `DecisionPanel` 저장 이후 사용자가
   다음에 뭘 해야 할지 한 번도 고민하지 않게 만든다.
3. **근거·모델 판단·관리자 판단은 같은 화면에서 위상이 다르게 보여야 한다** — 셋을 같은
   카드 스타일로 나란히 두지 않는다(현재 문제 d의 해결).
4. **한 화면에 하나의 운영 질문만 둔다** — 운영 홈은 "오늘 누굴 먼저 볼까", 워크리스트는
   "이 조건에 맞는 사람이 몇 명인가", 상세는 "이 사람에게 무슨 일이 있었나"만 답한다.
5. **화려한 표현은 클릭 가능한 운영 행동으로 이어질 때만 쓴다** — 정적 장식이면 뺀다.
6. **시그니처 장면은 전체 서비스에 1~2개로 제한한다** — 모든 화면에 새 시각화를 넣지
   않는다.
7. **이미 있는 걸 먼저 켜고, 그다음에 새로 만든다** — Trust Center의 버전 비교처럼 이미
   구현됐지만 안 보이는 것부터 정리한다.

## 8. 제한 없이 발굴한 전체 아이디어 목록

### A. 운영 효율 기능
- A1. **Triage Focus Mode** — 판단 저장 즉시 다음 미검토 대상으로 자동 이동 + `1`~`4`
  단축키로 판단 옵션 선택 + `←`/`→`로 이전/다음 이동 (이미 있는 prev/next 구조 위에
  얹는 확장)
- A2. **워크리스트 원키 스캔** — `ReviewerTable`의 각 행에서 스페이스/엔터로 우측
  프리뷰 패널을 열어 목록을 벗어나지 않고 다음 사람을 훑어보기 (Salesforce Split View
  재해석, 단 별도 상세 페이지 이동 없이)
- A3. **판단 완료 상태의 명시적 시각 분리** — 워크리스트에서 완료 항목을 흐리게 하거나
  체크 아이콘으로 눈에 띄게 구분(현재는 상태 텍스트 필터만 있음)
- A4. **Reviewer Momentum Strip** — 워크리스트 각 행에 리뷰 수·활동월·간격·탐색 변화
  방향을 CSS bar 4개로 압축해 표를 열지 않고도 스캔 가능하게
- A5. **큐 진행률 표시** — 운영 홈/워크리스트 상단에 "오늘 N명 중 M명 처리" 진행 바
  (localStorage 판단 수 기준)
- A6. **다음 대상 프리페치** — 상세 페이지 진입 시 다음 리뷰어의 상세 JSON을 미리
  fetch해서 다음 이동 시 로딩 문구 없이 전환(성능 개선, 신규 데이터 불필요)

### B. 시각적 시그니처 기능
- B1. **Retention Pulse** — 6,533명을 밀도 표현(집계형 도트/헥스빈)으로 그리고, 1,307명
  우선 검토 대상을 강조. 클릭 시 워크리스트로 이동.
- B2. **Activity Rhythm(활동 신호 스트립)** — Reviewer 360에서 월별 활동을 레이어드
  스트립으로. ECG/의료 표현 금지, "활동 신호 스트립"으로 명명.
- B3. **Evidence Constellation** — 근거 간 관계를 연결망으로. (아래 9번 검토에서 기각
  방향으로 결론)
- B4. **Intervention Path(개입 경로도)** — 활동 신호 → 위험 유형 → 모델 판단 → 관리자
  판단 → 플레이북을 가로 단계 다이어그램으로. 읽기 전용.
- B5. **Risk Story** — 상세 상단에 "언제부터·무엇이·어떻게 변했는지"를 3장면 카드로.
- B6. **Regional Cartogram(콘텐츠 공급 관측소)** — 지역 리스크를 타일 카토그램으로.
- B7. **Model Decision Lens** — 동일 리뷰어를 활동 변화/모델 판단/관리자 판단 세 탭으로
  전환.

### C. 발표 데모 기능
- C1. **Command Palette(⌘K)** — 리뷰어 이동, 플레이북 이동, 큐 필터를 검색으로.
- C2. **90초 가이드 투어 모드** — 정해진 6~8스텝을 자동 하이라이트하며 이동하는 발표
  전용 오버레이(실 데이터 위에서 동작, 가짜 화면 아님)
- C3. **정지 화면 히어로** — 운영 홈 최상단에 B1(Retention Pulse)을 배치해 "3초 안에
  핵심 메시지"를 만족.
- C4. **자연어 질의 바** — (신규 백엔드 필요, 아래 평가에서 보류)
- C5. **임팩트 시뮬레이션 프리뷰** — (검증되지 않은 예측 수치 필요, 도메인 위험으로
  아래 평가에서 제외)

## 9. 유사 아이디어 그룹

- **큐 자동 전진 그룹**: A1(Triage Focus Mode), Stripe/Linear 원키 패턴 → 하나의 기능으로
  통합.
- **전체 조망 그룹**: B1(Retention Pulse), C3(정지 화면 히어로) → 사실상 같은 장면. B1이
  C3의 구현체.
- **활동 변화 시각화 그룹**: B2(Activity Rhythm), B5(Risk Story) → B5가 B2를 포함하는

  Reviewer 360 상단의 한 섹션으로 통합 검토.
- **판단 경로 시각화 그룹**: B4(Intervention Path), B7(Model Decision Lens), B3(Evidence
  Constellation) → 셋 다 "근거→모델→관리자→플레이북 연결"을 표현하려는 시도. 네트워크
  그래프(B3)는 인과관계처럼 보일 위험이 커서 제외하고, B4(선형 경로도)로 수렴.
- **지역 관측 그룹**: B6 하나뿐이지만 이전 대화의 "리뷰 공급 변화 아티팩트" 이슈와 묶여
  있음 — 카토그램을 만들기 전에 데이터 이슈부터 참고(단, 이번 v05 UI 탐색 범위 밖).
- **검색/탐색 가속 그룹**: C1(Command Palette), C4(자연어 질의) → C1은 결정론적 라우팅
  (신규 데이터 불필요), C4는 별도 백엔드 필요. 난이도 차이가 커서 분리 유지.

## 11. 가장 강한 후보의 상세 설계

### 11.1 Triage Focus Mode (A1) — 운영 효율 핵심

- **콘셉트**: "판단하면 저절로 다음 사람이 온다."
- **분류**: 운영 효율 기능
- **해결하는 질문**: "이 사람 판단 다 끝났는데, 다음은 누구지?"를 매번 스스로 찾지 않게.
- **현재 문제 해결**: 위 3-c에서 지적한 "뼈대는 있는데 마지막 한 걸음이 비어 있다."
- **처음 보는 장면**: 워크리스트에서 "지금부터 검토 시작" 진입점(기존 "리뷰어 관리에서
  전체 대상 보기" 버튼 옆에 추가) → 첫 미검토 대상의 상세 화면.
- **시각적 중심**: `DecisionPanel` 내부, 4개 판단 옵션 라디오 각각에 `1`/`2`/`3`/`4`
  키캡 배지 표시.
- **상호작용**: 숫자키로 판단 선택 → 저장 버튼 클릭 또는 `Enter` → 저장 성공 토스트
  0.6초 → 자동으로 다음 미검토 리뷰어 라우트로 이동. `←`/`→`는 기존 prev/next 유지(임의
  이동), 자동 전진은 저장 시에만.
- **기존 데이터**: `reviewers` 배열, `decisionStorage`(그대로), `PriorityQueue`의
  정렬 로직.
- **새 데이터 필요**: 없음.
- **적용 화면**: `ReviewerDetailPage.jsx`, `DecisionPanel.jsx`.
- **연결**: A4(스트립)로 다음 대상을 판단 전에 미리 스캔, B1(Pulse)에서 진입.
- **참고 서비스**: Linear Triage(원키 상태 전이), Stripe Radar(prev/next + 종료 액션).
- **재해석**: 실제 액션(승인/환불/합병)이 아니라 "이 브라우저의 판단 기록"이라는 점을
  토스트 문구에 항상 포함(`"OO 님 판단 저장 · 이 브라우저 기준"`).
- **30초 데모**: 워크리스트에서 "검토 시작" 클릭 → 상세 진입 → `2`(리뷰 활동 늘리기) →
  저장 → 0.6초 후 자동으로 다음 리뷰어로 전환, 반복.
- **구현 난이도**: 낮음(현재 스택으로 바로 가능). 필요 기술: React state, `useNavigate`,
  `keydown` 리스너.
- **신규 라이브러리**: 불필요.
- **데이터 정합성 위험**: 낮음(기존 저장 로직 재사용).
- **성능 위험**: 낮음.
- **오해 가능성**: "자동으로 판단됨"으로 오해할 수 있음 → 반드시 사용자가 직접 선택한
  값만 저장, 자동 추천을 자동 저장하지 않는다는 문구 유지.
- **v05 추천**: **추천**. 리스크 최소, 임팩트 확실.

### 11.2 Retention Pulse (B1) — 시각적 대표 장면 핵심

- **콘셉트**: "6,533명의 활동 신호 속에서 1,307명이 스스로 드러난다."
- **분류**: 시각적 시그니처 기능 + 발표 데모 기능
- **해결하는 질문**: "이 서비스가 다루는 문제의 규모가 실제로 얼마나 되는가?"를 숫자
  3장짜리 카드가 아니라 한 장면으로.
- **비판적 검토(섹션 9의 조건 적용)**:
  - *개별 vs 집계 혼동 방지*: 6,533개 도트를 모두 그리면 성능·접근성 문제가 생긴다
    (섹션 12 참조). **결론: 집계형(그룹 묶음) 표현을 채택**하고, "한 셀 = 여러 리뷰어"
    임을 항상 범례에 명시한다. 개별 리뷰어를 보고 싶으면 클릭 → 워크리스트로 필터링해서
    이동(개별 탐색은 기존 화면에 위임, 여기서 직접 그리지 않음).
  - *장식용 파티클 금지*: 애니메이션은 최초 1회 진입 시 값 자체가 그려지는 정적 전환만
    허용(무한 반복 파티클 금지).
  - *선택 → 워크리스트 이동*: 각 셀 클릭 시 `riskType`/`modelJudgment` 필터가 적용된
    `/reviewers` 로 이동.
- **구현 방식 결정**(섹션 12 상세 비교 참고): **CSS Grid 기반 집계 타일(헥스빈이 아닌
  사각 그리드)**. 6,533명을 `priorityRank` 순으로 정렬 후 예를 들어 100명 단위로 묶어
  약 65개 셀을 만들고, 셀 색상 = 해당 그룹의 평균 위험 신호 강도, 셀 진하기 = 해당 그룹
  내 우선 검토 대상 비율. `Recharts`로는 이런 임의 그리드형이 어려워 순수 CSS
  grid + 인라인 style로 구현(신규 라이브러리 불필요).
- **처음 보는 장면**: 운영 홈 최상단, 기존 3개 `SummaryCard` 위(또는 대체) 배치.
- **적용 화면**: `OperationsPage.jsx`.
- **연결**: A1(Triage Focus Mode)의 진입점, B4(경로도)의 "발견" 단계.
- **참고 서비스**: Amplitude 코호트 매트릭스(집계 셀 개념만 차용, 매트릭스의 시간축
  구조는 차용하지 않음 — 이 프로젝트엔 코호트 시간축 데이터가 없음).
- **재해석**: Amplitude는 시간 경과별 리텐션 매트릭스지만, 이 프로젝트는 시계열 코호트가
  없으므로 "우선순위 순으로 묶은 밀도 타일"로 재해석 — 전혀 다른 축.
- **30초 데모**: 운영 홈 진입 → 타일 밀집 장면(65개 셀, 빨강 계열이 몰린 구간) →
  "이 빨간 덩어리가 통합 우선순위 상위 20%, 1,307명입니다" → 셀 클릭 → 워크리스트로
  이동, 필터 적용된 채로 표 등장.
- **구현 난이도**: 중(집계 로직 + CSS grid). 신규 라이브러리 불필요.
- **성능 위험**: 낮음 — 65~130개 DOM 노드 수준이라 가상화 불필요.
- **오해 가능성**: "셀 하나 = 리뷰어 한 명"으로 착각할 위험 → 범례에 "1칸 = 약 100명"
  명시 필수.
- **v05 추천**: **추천**. 단, 셀 단위(그룹 크기)는 실제 데이터로 픽셀 예산 계산 후 확정
  필요(구현 착수 전 확인 사항으로 섹션 23에 명시).

### 11.3 Intervention Path (B4, B7 흡수) — 판단 경로 핵심

- **콘셉트**: "근거 → 모델 판단 → 관리자 판단 → 플레이북"이 한 줄로 보인다.
- **분류**: 시각적 시그니처 + 운영 효율
- **비판적 검토**: 원안(섹션 9의 조건)대로 네트워크 그래프(Evidence Constellation)는
  기각 — 근거들 사이의 "연결 강도"를 데이터로 정의할 수 없어 인과관계처럼 보일 위험이
  크다. 대신 **선형 5단계 경로**로 단순화: `핵심 활동 변화 → 위험 유형 → 모델 판단
  (참고) → 관리자 판단(결정) → 플레이북(다음 행동)`. 각 단계는 이미 존재하는 데이터
  필드(`coreChange`/`riskType`/`modelJudgment`/`managerDecision`/`strategy.title`)를
  그대로 나열하는 것이라 새 계산이 없다.
- **처음 보는 장면**: 리뷰어 상세 페이지, 현재 `EvidenceList` + 전략 카드 +
  `DecisionPanel`이 세로로 쌓인 자리에 상단 요약 경로 바 추가.
- **시각적 중심**: 5개 단계를 가로 화살표로 잇는 얇은 스트립(카드 아님 — 문제 b의
  "카드 과다" 반복을 피함). 관리자 판단 전에는 4번째 칸이 "미정"으로 회색 처리.
- **상호작용**: 각 단계를 클릭하면 해당 상세 섹션으로 스크롤(앵커).
- **적용 화면**: `ReviewerDetailPage.jsx` 상단.
- **연결**: B7(Model Decision Lens)의 "모델 vs 관리자 역할 분리" 원칙을 3번째/4번째
  칸의 시각적 구분(모델=아웃라인, 관리자=채움)으로 흡수.
- **참고 서비스**: Braze Canvas(분기 경로 개념, 단 읽기 전용으로 재해석), Salesforce
  Feed(시간순 배치 감각).

## 21. 기술적 위험과 성능 위험

- **B1 Retention Pulse 집계 로직**: `reviewers` 6,533건을 그룹핑하는 계산은 클라이언트
  1회 `useMemo`로 충분(정렬된 배열을 100개 단위 slice) — 성능 위험 낮음. 다만 그룹 크기
  기준(100명? 50명?)은 실제 데이터 분포를 봐야 결정 가능 — 구현 전 확인 필요.
- **A1 자동 전진 시 라우팅 경쟁 상태**: `useNavigate` 호출 직후 다음 리뷰어의
  `loadReviewerDetails()` fetch가 다시 실행되며 로딩 깜빡임이 생길 수 있음(현재
  `ReviewerDetailPage`는 리뷰어마다 remount됨). 완화책: A6(다음 대상 프리페치)를 A1과
  같이 묶어 구현.
- **키보드 단축키 충돌**: 브라우저 기본 단축키(숫자키는 대체로 안전)와 폼 입력 포커스
  상태에서의 오작동 방지 필요 — `input`/`textarea` 포커스 시 단축키 비활성화 처리 필수.
- **신규 라이브러리**: 이번 3개 핵심 후보는 모두 **신규 라이브러리 불필요**(React +
  Tailwind + 순수 CSS/SVG). 번들 크기 영향 없음.
- **지도/카토그램(B6, 보류 후보)**: 실제 미국 주 지형 지도를 쓰려면 지도 라이브러리가
  필요해 발표 전 리스크가 커짐 — 채택 시에도 **지형 지도가 아닌 타일 카토그램**으로
  제한할 것을 권고(섹션 12 스택 적합성 참고).

## 23. 구현 전 확인해야 할 질문

1. **Retention Pulse 그룹 크기** — 6,533명을 몇 명 단위로 묶을지(50/100/200명)는

5. **A3(완료 상태 시각 분리)를 워크리스트 어떤 시각 언어로 할지** — 흐림 처리 vs 체크
  아이콘 vs 별도 컬럼, 접근성(색맹 대응) 고려해 확정.
6. **발표 리허설 일정** — C2(가이드 투어 모드)를 넣을지는 발표 전 리허설 시간이 며칠
  남았는지에 달려 있음 — 시간이 촉박하면 스킵.

## 최종 결론

> v05의 대표 장면은 **운영 홈의 Retention Pulse**이다.
>
> 이 장면이 보여주는 데이터는 **전체 리뷰어 6,533명의 우선순위 분포와, 그중 통합
> 우선순위 상위 20%인 1,307명이 어디에 몰려 있는지**이며, 운영상의 핵심 가치는
> **"오늘 누굴 먼저 봐야 하는가"라는 질문에 3초 안에 답한다는 것**이다.
>
> 이 장면에서 운영자는 **위험이 몰린 구간**을 확인하고, **어느 그룹부터 검토할지**를
> 판단한 뒤, **워크리스트를 거쳐 Triage Focus Mode로** 이동한다.
>
> 발표에서 관객이 기억해야 할 한 문장은
> **"이 서비스는 6,533명 중 누구를, 왜, 어떻게 먼저 봐야 하는지 알려주고, 판단이
> 끝나면 스스로 다음 사람에게 데려간다"**이다.

**추가 질문에 대한 답**

- **단 하나만 구현한다면**: A1 Triage Focus Mode. 발표 임팩트는 B1보다 약하지만,
  "이게 없으면 실제로 더 불편한가?"에 유일하게 명확히 "그렇다"고 답할 수 있는 기능이며
  구현 위험이 가장 낮다.
- **시각 기능 하나 + 운영 기능 하나를 조합한다면**: B1(Retention Pulse) + A1(Triage
  Focus Mode). Pulse가 "누구부터"를 보여주고 Triage가 "그다음 어떻게"를 처리한다 —
  발견과 행동의 완결된 짝.
- **구현 시간이 절반으로 줄면 남길 것**: A1만 남긴다. Pulse는 시안 검토(그룹 크기 확정)
  없이 서두르면 오독 위험(체크리스트 22)이 커지므로, 시간이 부족하면 안전한 쪽을
  우선한다.
- **정지 화면 한 장으로 발표해야 한다면**: Retention Pulse가 그려진 운영 홈 스크린샷.
  숫자 카드보다 "규모 + 위험이 몰린 구간"을 한눈에 보여주기 때문.
- **이 장면이 실제 데이터/운영 행동과 연결되는 방식**: 타일은 실제 `priorityRank`·
  `modelJudgment` 값으로 색이 정해지고(장식 아님), 클릭하면 실제 필터가 걸린
  `/reviewers`로 이동하며, 거기서부터는 이미 존재하는 실제 판단 저장·플레이북 딥링크
  로직을 그대로 탄다 — 새 화면이 아니라 기존 운영 흐름의 입구일 뿐이다.
