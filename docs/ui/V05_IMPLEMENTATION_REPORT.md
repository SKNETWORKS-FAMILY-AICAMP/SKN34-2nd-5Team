# v05 구현 및 검증 보고서

작성일: 2026-07-31  
대상: React 운영 서비스 `app/` + FastAPI `api/` + MySQL `yelp_data`

## 1. 목적과 범위

v05는 발표 전 마지막 프런트 고도화로, 운영자의 발견→검토→판단→행동 흐름을
강화하고 시각적으로 기억되는 장면을 추가한다. 기존 모델·코호트·시간 분할을
바꾸지 않고 B 기능과 G 파생 데이터를 실제 서비스에 연결했다.

팀원 소유의 기존 `pipeline/`, `database/`와 충돌하지 않도록 추가 파생·DDL·로더는
`v05/`에 격리했다. 자세한 재현 절차는 [`v05/README.md`](../../v05/README.md)를
따른다.

## 3. 주요 화면 변경

### 운영 홈

- Signal Atlas로 최근 활동 월×마지막 리뷰 경과일 구간을 표현한다.
- 셀 색은 이탈 확률이 아니라 검토 대상 비율이다.
- 셀 선택 시 워크리스트 필터 문맥으로 이동한다.

### 리뷰어 관리

- Split View에서 목록과 리뷰어 근거·판단을 함께 본다.
- URL이 필터 상태의 기준이며 딥링크, 새로고침, 뒤로가기를 지원한다.
- Evidence cross-highlight, 진행률, Command Palette를 연결했다.

### Reviewer 360

- Decision Rail과 Activity Story Stage로 변화→모델 참고→관리자 판단을 분리했다.
- 2017/2018 P90 리뷰 활동 반경과 음식점 상대 분포를 표시한다.
- 각 기간 중심을 원점으로 재배치하며 거주지·직장·생활권을 나타내지 않는다.
- 원거리 활동은 별도 목록으로 표시하며 여행이라고 단정하지 않는다.

### 플레이북

- 리뷰어 문맥으로 진입하면 해당 판단 플레이북을 먼저 보여준다.
- DB에 추천 데이터가 있을 때 미방문 음식점 후보 최대 3곳을 표시한다.
- 추천은 방문·리뷰 작성 예측이 아닌 운영 참고 후보로 표현한다.

### 콘텐츠 위험

- 권역 우선순위, 탐방 범위, 리뷰 공급 변화의 세 관점을 제공한다.
- 탐방 반경은 위험 피처가 아니라 캠페인 거리 범위 참고값이다.
- 리뷰 공급은 파워 리뷰어 코호트가 아닌 전체 음식점 리뷰로 재계산했다.

## 4. G-1 개인 맞춤 음식점 추천

기준:

- 선정연도 종료까지 리뷰하지 않은 음식점
- 긍정 리뷰(4~5점)의 세부 카테고리 선호
- `Restaurants`, `Food`, `Nightlife` 등 일반 카테고리 제외
- 개인 P90 반경→1.5배→최대 50km 확장 계약
- `is_open = 1`, Yelp 별점 3.5 이상, 리뷰 10건 이상
- 리뷰어당 최대 3곳, 대표 카테고리 중복 금지

결과:

| 항목 | 값 |
|---|---:|
| 추천 리뷰어 | 6,456명 |
| 추천 후보 | 19,351곳 |
| 3곳 추천 | 6,446명 |
| 2곳 추천 | 3명 |
| 1곳 추천 | 7명 |
| 조건 충족 후보 없음 | 77명 |
| 과거 방문 음식점 포함 | 0건 |
| 최대 거리 | 49.34km |

77명은 조건을 완화해 임의 후보를 채우지 않았다. 음식점의 `is_open`, 별점,
리뷰 수는 Yelp 데이터셋 스냅샷 속성이며 선정연도 시점의 별도 스냅샷이 아니라는
제한이 있다. 모델 피처나 예측 결과에는 사용하지 않는다.

## 5. G-2 전체 리뷰 공급 변화

`restaurant_reviews` 전체를 `restaurant_businesses`의 음식점 주와 결합했다.
모델의 최종 선정연도 이후 데이터는 포함하지 않고 2009~2018년만 집계했다.

| 항목 | 값 |
|---|---:|
| 권역 | 14개 |
| 기간 | 2009~2018년 |
| 산출 행 | 140행 |
| 2017 리뷰 | 552,439건 |
| 2018 리뷰 | 610,672건 |
| 전체 변화 | +10.5% |
| 권역 변화 범위 | AB -1.2% ~ ID +21.6% |

기존 코호트 기반 지표의 전 권역 +50~145% 증가는 선정 조건의 구조적 편향이었다.
전체 리뷰 기준으로 재계산해 화면에 다시 연결했다.

## 12. 운영 데이터 서버 저장

2026-07-31 로컬 `yelp_data`에 다음 테이블을 추가했다.

| 테이블 | 역할 |
|---|---|
| `retention_decisions` | 리뷰어별 현재 판단·메모·담당자·스누즈 |
| `retention_decision_history` | 생성·수정·삭제 append-only 감사 이력 |
| `retention_interactions` | 접촉 채널·시점·메모 |

판단의 현재 상태는 모델 표본이 아니라 `reviewer_user_id`에 귀속하고,
`model_version + sample_id`는 판단 당시 모델 문맥으로 보존한다. 동시에 수정할 경우
`lock_version`으로 충돌을 감지한다. 기존 localStorage 판단은 이관하지 않았다.

React의 운영 홈·리뷰어 관리·Reviewer 360·플레이북은 하나의
`DecisionContext`를 사용하며 서버 저장 직후 모든 화면의 상태와 진행률이 함께
갱신된다. Reviewer 360에는 판단 메모, 재검토 시점, 접촉 이력 입력을 추가했다.

현재 브랜치에는 팀 로그인·회원가입 코드가 없어 `api/auth_context.py`가 서버 설정의
개발 운영자를 감사 주체로 사용한다. 로그인 병합 후 이 함수가 세션/JWT의 불변 사용자
ID와 표시명을 반환하도록 교체한다. 계정 테이블은 중복 생성하지 않았고 담당자 선택은
사용자 목록 API가 확인될 때까지 활성화하지 않았다.

검증 결과:

- 운영 테이블 3개 생성 확인
- `GET /api/retention/decisions` 실제 DB 응답 200
- 존재하지 않는 표본의 저장 요청 422 방어 확인
- 정상 판단·감사 이력 INSERT 경로를 트랜잭션 안에서 확인 후 롤백
- 운영 데이터 검증 SQL 5개 항목 모두 0건
- React 프로덕션 빌드 성공
- 실제 브라우저에서 서버 진행률 문구와 판단·메모·스누즈·접촉 UI 확인
- 브라우저 콘솔 오류 0건

## 13. 대상 명단 서버 저장 (F-5)

2026-07-31 로컬 `yelp_data`에 `target_lists`, `target_list_members` 테이블을
추가했다. 플레이북 화면의 "대상 명단에 추가" 저장은 브라우저 localStorage
대신 서버에 기록되며, 새로고침·다른 브라우저에서도 동일하게 조회된다.

| 테이블 | 역할 |
|---|---|
| `target_lists` | 명단 이름·기준 판단·모델 버전·생성자 |
| `target_list_members` | 명단에 속한 리뷰어(중복 자동 제거) |

`target_list_members`는 `retention_interactions`와 동일하게
`(model_version, sample_id)` 외래키로 `model_predictions`를 참조해 존재하지
않는 리뷰어 표본이 명단에 들어가지 못하게 한다. 생성 시 중복
`reviewer_user_id`는 서버에서 제거하고 `duplicatesRemoved` 값으로 응답한다.
삭제는 `target_lists` 행 삭제로 소속 멤버까지 `ON DELETE CASCADE`로 함께
제거된다.

API:

| API | 용도 |
|---|---|
| `GET /api/retention/target-lists` | 전체 명단과 소속 리뷰어 조회 |
| `POST /api/retention/target-lists` | 명단 생성(중복 제거, 감사 주체 기록) |
| `DELETE /api/retention/target-lists/{list_id}` | 명단 삭제(멤버 함께 삭제) |

검증 결과:

- DDL 적용 확인 (`target_lists`, `target_list_members` 생성)
- `validate_target_lists.sql` 4개 항목 모두 `issue_count = 0`
- API로 실제 리뷰어 1,163명 명단 생성 → 조회 → 삭제까지 왕복 확인
- 존재하지 않는 리뷰어 표본으로 생성 시 422 방어 확인
- 대상 ESLint 통과(플레이북 화면 관련 신규 코드에 오류 없음)
- React 프로덕션 빌드 성공
- 실제 브라우저에서 명단 저장 피드백 문구·CSV 내보내기·삭제 버튼 동작 확인
- 브라우저 콘솔 오류 0건

기존 `targetListStorage.js`(localStorage)는 사용처가 없어져 삭제했다.

## 14. 리뷰어 상세 단건 API 전환 (H-1)

`GET /api/reviewer-details`(전체 6,533명 상세를 한 번에 반환)를 제거하고
`GET /api/reviewer-details/{user_id}`로 교체했다. 기존 방식은 Reviewer 360
화면 하나만 열어도 월별 활동까지 포함한 전체 리뷰어 상세를 한 번에
내려받았다 — 실제로 화면은 한 번에 리뷰어 한 명만 보여준다.

- `api/services/reviewer_detail_service.py`의 `get_reviewer_details()`를
  `get_reviewer_detail(engine, user_id)`로 교체. SQL에 `user_id` 조건을 추가해
  DB 조회 자체를 단건으로 좁혔다(월별 활동 조인 포함).
- React `app/src/data/index.js`의 `loadReviewerDetails()`(전역 캐시 1개)를
  `loadReviewerDetail(userId)`로 교체. 리뷰어별 캐시(Map)로 바꿔 같은
  리뷰어를 다시 열 때는 재요청하지 않는다(B-11 동작 유지).
- 호출부 `ReviewerDetailPage.jsx`, `ReviewerSplitPanel.jsx` 모두 단건 API로
  전환.

검증 결과:

- 기존 `/api/reviewer-details` 벌크 엔드포인트 제거 확인(404)
- `/api/reviewer-details/{user_id}` 정상 응답, 존재하지 않는 리뷰어 404 확인
- 단건 응답이 기존 `build_detail()` 출력과 동일한 필드 구성인지 확인
  (userId/priorityRank 등은 원래도 프런트가 `reviewer` 객체에서 병합)
- 대상 ESLint 통과, React 프로덕션 빌드 성공
- 실제 브라우저에서 Reviewer 360과 리뷰어 관리 Split View 모두 단건 API로

## 16. 번들 코드 분할

`app/src/App.jsx`의 6개 라우트 컴포넌트를 `React.lazy()` + `Suspense`로
전환했다. 기존에는 화면 하나만 열어도 `recharts`를 포함한 단일 749.9KB
번들 전체를 내려받아 500KB 경고가 있었다 — `recharts`는 실제로 Trust
Center와 Reviewer 360(활동 요약·리뷰 간격·월별 타임라인 차트)에서만
쓰인다.

변경 후 진입 번들은 242KB(gzip 78KB)로 줄었고, 화면별 청크(11~33KB)와
`recharts` 청크(387KB)는 해당 화면을 열 때만 지연 로드된다. 라우트 전환
중에는 기존 `Skeleton` 컴포넌트를 `Suspense` fallback으로 재사용해 별도
로딩 UI를 새로 만들지 않았다.

검증 결과:

- 대상 ESLint 통과
- React 프로덕션 빌드 성공, 500KB 청크 경고 해소(진입 번들 242KB)
- 브라우저에서 운영 홈 → 모델 신뢰(Trust Center) → Reviewer 360 이동 시
  각 화면이 정상 렌더링되는 것을 실측 확인(차트·표 데이터 포함)
- 콘솔 오류 0건

## 17. 리뷰어 관리 Split View → Reviewer 360 진입 링크

사용자 확인 과정에서 `/reviewers`(리뷰어 관리 Split View) 화면에 Reviewer
360 전체 페이지(`/reviewers/:id`)로 가는 경로가 전혀 없다는 사실을
발견했다. 목록 행과 우측 판단 패널(`ReviewerSplitPanel.jsx`) 모두 리뷰어
ID가 일반 텍스트였고, "저장하고 다음 미검토" 버튼은 목록 내 다음 미검토
행으로 넘어갈 뿐 전체 페이지로 이동하지 않았다. Reviewer 360은 운영
홈·플레이북 표·Command Palette 세 곳에서만 진입 가능했다.

`ReviewerSplitPanel.jsx` 패널 상단에 `Reviewer 360 전체 보기` 링크
(`/reviewers/:id`)를 추가해 Split View에서 판단하다가 리뷰어의 반경·월별
타임라인·사후 검증 등 전체 맥락을 봐야 할 때 바로 이동할 수 있게 했다.

같은 확인 과정에서 이미 판단이 저장된 리뷰어를 다시 열었을 때 취소 수단이
없다는 점도 함께 발견했다. 저장 직후 뜨는 확인 토스트에만 "실행 취소"가
있었고, 패널을 닫았다가 다시 열면(예: 다른 리뷰어를 봤다가 돌아옴) 판단을
취소할 방법이 없었다 — 전체 페이지의 `DecisionPanel.jsx`에는 이미 상시
"취소" 버튼이 있어 두 화면 동작이 어긋나 있었다. "판단 완료 · {decision}"
줄 옆에 상시 "취소" 버튼을 추가해 두 화면 동작을 맞췄다(기존 `handleUndo`
재사용, 새 삭제 로직 없음).

검증 결과:

- 대상 ESLint 통과, React 프로덕션 빌드 성공(청크 경고 없음)
- 브라우저에서 링크 클릭 시 `/reviewers/:id`로 정상 이동하는 것을 확인
- 브라우저에서 실제로 판단 저장(`PUT`) → 패널 재확인 → 취소(`DELETE`)까지
  왕복해 두 요청 모두 200 응답, 화면에서 판단 완료 표시가 사라지는 것을
  확인

## 18. 운영 홈 QA 반영

사용자와 화면별 점검을 운영 홈부터 시작하며 다음을 반영했다.

- **헤더 "React 전환 검증 중" 제거**: 데이터 연동 상태와 무관하게 하드코딩된
  고정 문구였다. React→API+MySQL 전환은 2026-07-30 완료로 이미 기록돼
  있고, 이번 세션에서 F-5·H-1·QA·번들 분할까지 전부 실 서버 데이터로
  검증했으므로 "검증 중" 문구가 가리키는 상태는 지나갔다. "PROJECT DATA ·
  V04" 배지는 유지했다 — 이건 실제 운영 중인 모델 버전(`model_version =
  'v04'`, DB 전체에 태깅된 값)을 보여주는 것이라, 이번에 진행한 프런트
  고도화 코드네임인 "v05"와 혼동해 바꾸면 안 된다고 판단해 사용자와 합의로
  보류했다. 새 모델이 실제로 배포되면 그때 갱신한다.
- **하단 공백 해소**: "이 큐는 왜 우선인가"(`PolicyPanel`)가 `max-w-md`로
  폭이 좁게 고정된 채 두 컬럼 레이아웃 아래 혼자 놓여 있어 그 오른쪽 전체가
  빈 공간으로 남아 있었다. 우측 컬럼("오늘 먼저 볼 5명" 아래)으로 옮겼다.
  다만 이 상태에서는 `grid` 기본값(`align-items: stretch`)이 Signal Atlas
  카드를 더 길어진 오른쪽 컬럼 높이에 맞춰 늘려버려, 카드 테두리 안쪽에
  다시 빈 공간이 생겼다(사용자가 스크린샷으로 지적). 그리드 컨테이너에
  `items-start`를 추가해 각 컬럼이 자기 내용만큼만 높이를 갖도록
  고쳤다(실측 결과 카드 내부 여백이 1509px → 17px로, 정상 패딩 수준까지
  줄어듦).
- **Signal Atlas Y축 설명 추가**: X축("마지막 리뷰 후 경과일")에는 캡션이
  있었지만 Y축(최근 활동 개월 수, 12→3)은 아무 설명이 없었다 — 캡션을
  추가했다.
- **Signal Atlas 색상 범례 추가**: 셀 배경색이 검토 대상 비율을 낮음→높음
  그라데이션으로 인코딩하는데 범례가 없었다 — 테두리·"—" 범례 옆에
  그라데이션 바를 추가했다.
- **PriorityQueue 리뷰어 ID 잘림 보완**: "오늘 먼저 볼 5명" 목록의 ID가
  `truncate`로 잘리는데 hover해도 전체 값을 볼 수 없었다 — `title` 속성을
  추가했다.
- **Signal Atlas 중복 캡션 제거**: Y축 캡션을 상단에 추가하면서 격자 하단의
  기존 "마지막 리뷰 후 경과일 →" 캡션과 내용이 겹쳤다 — 하단 캡션을
  제거하고, 그 자리에 격자가 실제로 몇 명을 반영하는지 보여주는 커버리지
  문구("격자에 포함된 리뷰어 N명 / 전체 M명")를 넣었다. 지어낸 문구가
  아니라 `grid` 집계값에서 실시간으로 계산한 값이며, 향후 리뷰어가 어떤
  구간에도 속하지 못해 조용히 누락되는 경우를 감지하는 신뢰 지표로도
  쓰인다.

검증 결과:

- 대상 ESLint 통과, React 프로덕션 빌드 성공(청크 경고 없음)
- 브라우저에서 헤더 텍스트, Y축·색상 범례 캡션, ID 툴팁 실제 렌더링 확인
- 좌우 컬럼 하단 높이가 픽셀 단위로 일치하는 것을 `getBoundingClientRect()`로
  실측 확인
- 콘솔 오류 0건
